## Step 3: cost-export storage, 22 October 2026

- Terraform from Windows failed before planning: the provider plugin's local gRPC handshake hit
  `x509: certificate signed by unknown authority`, because the machine's antivirus inspects
  local TLS. Switched to Terraform in WSL, the convention the earlier projects use.
- Plan: 3 to add (resource group, storage account, container). Hierarchical namespace on, shared
  keys off, public network access on with Entra-only access, TLS 1.2, HTTPS only.
- Applied 07:09–07:12 (the storage account took 1 min 30 s). A follow-up plan showed no changes.

## Step 4: cost exports, 22 October 2026

- The first create failed: `RP Not Registered ... Microsoft.CostManagementExports`. Registering
  the resource provider (free) fixed it after a few minutes.
- Two exports: a daily month-to-date export (CSV, gzip, overwrite, partitioned) and a one-time
  export for 1–30 September. The one-time export still needs a schedule field (`The Schedule
  field is required`), set inactive.
- Each export's identity holds one role, Storage Blob Data Contributor on the container only.
  Both runs completed at 07:33 with shared keys off.
- Listing the exported files then failed: the owner's own account had no data-plane role. A
  read-only role on the container alone fixed it.
- The layout and manifest matched what the code expects; the header (65 columns, data version
  2021-10-01) resolved through the column aliases with no code change.
- **September held only 30 September** (12 lines, 0.0018 AUD): the subscription changed offer
  that day, and Cost Management doesn't export costs from before the change.
- The same day, a local run of the whole pipeline on the real inputs passed all four checks
  twice with an identical re-run.

## Step 5: Fabric user and tenant settings, 22 October 2026

## Step 6: the Fabric trial, 22 October to 9 November 2026

- **22 October:** "A Fabric trial isn't available for your account." The tenant was 73 days old;
  community answers (not Microsoft's documentation) say trials need a tenant of 90 days.
- **30 October:** refused again.
- **7 November, 20:46** (8 November in Brisbane, when the tenant reached 90 days): the
  activation reported success, but no trial capacity existed. A support case was raised.
- **9 November:** after re-checking the settings support asked about (all already allowed), the
  retry worked: an F64 trial (FTL64, 64 capacity units, Australia East), ending about
  8 January 2027.
- Cost: 18 days of waiting. The offline work (the exchange-rate handling, hardening, and the code
  for projects 10–12) went on meanwhile.

## Step 8: workspaces, 9 November 2026

- Device-code sign-in for the Fabric admin was blocked by the tenant's security defaults
  (`AADSTS530035`). Interactive browser sign-in from WSL worked; security settings weren't changed.
- Terraform created both workspaces, but **prod's workspace identity failed on create**
  (`InternalError`). Terraform tainted the workspace. Provisioning through the API first returned
  `WorkspaceIdentityAlreadyExists`; deprovisioning and provisioning were then accepted (202) but
  changed nothing; deleting the failed identity in the portal and
  creating it again worked, and a second apply finished the role assignment.
- Both workspaces assigned to the trial capacity through the API (Terraform's provider doesn't
  support trial capacity). Spark settings were already as needed (runtime 2.0).
- Both workspace identities given Storage Blob Data Reader on the export storage; a Fabric
  connection created with workspace-identity sign-in for the shortcut. Its first create failed on
  an empty path (`The Value field is required`); leaving the path out worked.

## Step 9: repo, environments and the first deploy

- **22 October:** the repo went public with secret scanning and push protection on; `dev` and
  `prod` environments (prod needs the owner's approval and accepts only `main`); a ruleset makes
  `main` pull-request-only with the `test` check required. The first CI run passed in 27 minutes.
- **9 November:** the first dev deploy **failed at sign-in** (`AADSTS700213`, no matching

  credentials fixed it.
- The re-run then failed at the wheel upload because the lakehouse didn't exist yet, as
  expected before step 10.

## Step 10: git sync to dev, 9 November 2026

- A fine-grained token (this repo only, contents read/write) connects dev to git.
- **The first "Update from Git" failed**, rejecting the real-time dashboard
  (`InvalidArtifactDefinitionFormat`). Moving items out one at a time showed three more Fabric
  rejects: the Activator (`The importArtifactRequest field is required`), the Eventstream (its

  (`Dataset_Import_FailedToImportDataset`, "Fabric artifact empty GUID not found").
- **Update from Git isn't reliably atomic:** the first failed attempt created nothing, but a later

  four items out; that sync succeeded.
- Checked against the repo: the lakehouse is schema-enabled; the pipeline's notebook references

## Step 15: capacity, 10–14 November 2026

- The Capacity Metrics app was connected on 10 November. Its first readings, up to 07:52 that
  day: one prod load about 1,884 CU-seconds, a peak of 0.62%, nothing rejected.
- The app's import refresh runs once a day at midnight Brisbane time, which looked like a day's
  wait before each run could be read. It isn't: the usage tables are DirectQuery. A query gets rows
  only when it sets the model's capacity parameter (`CapacitiesList`), and then a run shows
  minutes after it ends. `tools/capacity_report.py` reads them that way through the Power BI REST
  API.
- Scheduled runs 1 and 2 fired at 06:00 Brisbane time on 12 and 13 November, which confirms the
  schedule's time zone. Both passed all four checks. Run 3: **pending** (14 November).
- To 13 November: four prod runs used 1,587–2,417 CU-seconds each; nothing was throttled,
  rejected or billed as overage; the peak was 0.67%. The figures and the smallest paid size are
  in the [README](../README.md#capacity).

## Step 16: the three answers, 10 November 2026

Measured from a copy of prod's gold taken after the first prod run, with the package's own
answer functions. They're in the [README](../README.md#the-answers). Each published figure the
checks guard (project 1's $2.7055, project 3's 59 and 57, project 2's +0.271) came out the same.

A review of the drafts on 10 November found that project 1's citation and must-contain means
were averaged over every answer, including those the metrics don't apply to (the unanswerable
questions, and questions with nothing to contain). The private extract had dropped the study's
rule.

The fix ([#17](https://github.com/DmitryLyubaev/llm-cost-quality-fabric/pull/17), on `main`
through [#18](https://github.com/DmitryLyubaev/llm-cost-quality-fabric/pull/18)) has the extract
read the study's golden queries and leave a measure empty where it doesn't apply, so every mean
skips it. Dev got the fix first (11:01, re-run passed). Later on 10 November (11 November in
Brisbane) it was deployed to prod, the new extract uploaded, and prod re-run for 10 November
(19:37–19:42): a new baseline, since the code had changed, and every check passed. Re-measured
from prod's gold, project 1's citation and must-contain means now equal the study's own figures
(the README's table). Groundedness and the other studies' figures came out as before. After
both re-runs, dev's and prod's gold matched on 8 of 9 tables, and the ninth row for row apart
from first-seen load dates.
